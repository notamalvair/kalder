# Backend: микрозадачи

Цель первой версии: посетитель вводит домен и email, получает подтверждение принятия заявки; фоновое задание формирует HTML-отчёт и отправляет его на указанный email. Согласие на маркетинговую рассылку — отдельная будущая функция; оно не должно автоматически включаться при заказе отчёта.

Исходный n8n workflow используется как описание проверок. Его сбор компаний через Overpass, расписание и Google Sheets не нужны для пользовательской заявки. Адрес получателя берётся из формы, а не из email, найденных на проверяемом сайте.

## Прогресс

1. **Готово:** чистый модуль `audit.mjs` и проверки `audit.test.mjs`.
2. **Готово:** `fetch-site.mjs`: HTTP(S), только стандартные порты, проверка всех DNS-ответов и каждого redirect против SSRF, закрепление проверенного IP на соединение, лимит HTML 1 МБ, общий таймаут 15 секунд, до четырёх redirects. Переход HTTPS → HTTP запрещён. Проверка TLS остаётся включённой.
3. **Готово:** API принятия заявки с валидацией домена/email, лимитами, SQLite-хранением заданий и фоновым обработчиком с восстановлением после прерывания.
4. **Готово локально:** HTML/текстовый отчёт на немецком с экранированием данных сайта, файловый почтовый адаптер и адаптер Resend. Реальная доставка требует настройки провайдера и отправителя и пока не проверена.
5. **Готово локально:** форма сайта подключена к API через Vite proxy, показывает принятие заявки, обработку и результат тестового сохранения / принятия провайдером. Сквозной тест в Chromium проверяет полный путь до локального письма.

Проверка текущего этапа: `node --test backend/*.test.mjs` из корня проекта. Все 27 тестов проходят. Дополнительно `python backend/browser_check.py` запускает Chromium, Vite, API, SQLite и оба worker на временных данных. Нужны Python Playwright и `/usr/bin/chromium`; это инструменты проверки, не зависимости приложения. Тест проходит путь Website Check → форма с доменом/email → API → загрузчик с локальным тестовым транспортом → отчёт → файл письма, проверяет валидацию и текст режима реального провайдера на подставном ответе. Настоящие письма не отправляются. Новых npm-зависимостей нет.

## Запуск API

Из корня проекта: `node backend/server.mjs`. Нужна Node.js 22.13+ с доступным `node:sqlite`; проверено на Node 24.19.0. По умолчанию API слушает только `127.0.0.1:3001`, база создаётся в игнорируемой `.runtime/backend/jobs.sqlite`. Переменные `KALDER_API_HOST`, `KALDER_API_PORT`, `KALDER_DB_PATH` меняют адрес и расположение базы. Каталог базы должен оставаться на постоянном диске с ограниченным доступом; SQLite-база содержит email и результаты анализа. Не добавлять её в Git.

- `GET /api/healthz`: проверка HTTP-сервера.
- `POST /api/audits`, JSON `{"website":"example.com","email":"visitor@example.org"}`: HTTP 202, непрозрачный id и `Location` для статуса. Это принятие заявки, не обещание доставленного письма.
- `GET /api/audits/:id`: только id, состояние и код ошибки, без email и содержимого отчёта. Id является секретной ссылкой доступа к статусу; не публиковать его в аналитике.

Состояния: `queued → processing → report_ready` либо `failed`. Готовый отчёт пока хранится как JSON для следующего этапа. Очередь обрабатывает одно задание за раз в одном процессе. Аренда задания — 60 секунд, до трёх попыток восстановления после падения; устаревшая попытка не перезаписывает результат новой.

Ограничения: JSON до 4 КиБ, 5 принятых заявок с одного IP в час, 3 на один email в сутки, не более 100 ожидающих/обрабатываемых заданий. IP берётся из соединения, `X-Forwarded-For` не считается доверенным. При размещении за reverse proxy понадобится явно настроить доверенную передачу адреса, иначе посетители разделят один лимит. Завершённые записи старше семи дней очищаются при новых заявках; отдельный планировщик удаления данных ещё не добавлен. Нет настройки CORS: браузерную форму следует подключать через тот же origin и проксирование `/api`.

## Отчёт и почта

По умолчанию `KALDER_MAIL_MODE=file`: worker сохраняет JSON письма с получателем, темой, HTML и текстом в `.runtime/backend/outbox/<id>.json`. Файл имеет права 600, каталог создаётся с правами 700. `KALDER_OUTBOX_PATH` меняет каталог. Повторная попытка атомарно заменяет тот же файл. Это тестовый артефакт, не отправленное письмо. Он содержит email, хранить его вне публичной раздачи и Git. Автоматическая очистка файлов outbox пока не реализована; их нужно удалять отдельно по политике хранения.

Для реальной отправки предусмотрен `KALDER_MAIL_MODE=resend`. Требуются `KALDER_MAIL_API_KEY` и `KALDER_MAIL_FROM` с подтверждённым у провайдера отправителем. Значения задаются в защищённых настройках окружения, не в исходниках или чате. Нужен HTTPS-доступ к `api.resend.com`. При отсутствии конфигурации режим resend останавливается при запуске, без скрытого перехода на тестовый режим. В этой сессии проверялся только подставной ответ провайдера, реальных запросов отправки не было.

Worker доставки запускается вместе с API. Таблица `deliveries` добавляется без удаления имеющихся заданий. Состояния доставки доступны через поле `delivery` в статусе задания: `pending`, `sending`, `stored` (только локальный файл), `accepted` (принято провайдером) или `failed`. `accepted` не подтверждает попадание во входящие: для этого впоследствии потребуются подписанные webhook-события провайдера. Отчёт отправляется только на email из заявки, без добавления в маркетинговую базу.

При сбое выполняется до трёх попыток с паузами 30 и 60 секунд. Прерванная попытка восстанавливается после истечения 60-секундной аренды. Для Resend используется один idempotency key на задание. Гарантия провайдера ограничена его окном хранения ключа (24 часа); это не вечная гарантия exactly-once после произвольно долгого простоя.

Загрузчик использует прямые HTTP(S)-соединения без автоматического использования переменных HTTP_PROXY. Это необходимо учитывать при развёртывании в сети, разрешающей доступ только через прокси: поддержку доверенного прокси нужно проектировать отдельно, сохраняя защиту DNS/IP. Пробный прямой запрос `https://example.com` в текущей облачной среде завершился `getaddrinfo EAI_AGAIN example.com`. Поэтому загрузка реального внешнего сайта здесь пока заблокирована сетевым/DNS-ограничением. Сетевые и сквозные тесты выполнены на локальном HTTP-сервере через тестовый адаптер; он не включается никакой переменной production API. Ответы с неожиданным сжатием или кодировкой, отличной от UTF-8/ASCII, пока отклоняются явно.

## Запуск сайта вместе с API

Два терминала из корня проекта:

1. `node backend/server.mjs` — API и worker, по умолчанию локальные письма.
2. `npm run dev -- --host 127.0.0.1` — сайт; Vite проксирует `/api` к `127.0.0.1:3001`.

Если API расположен иначе, переменная `KALDER_API_PROXY_TARGET` задаётся процессу Vite. Vite preview также поддерживает этот proxy. Для проверки новой сборки: `npm run build -- --outDir .runtime/build`, затем `npm run preview -- --outDir .runtime/build --host 127.0.0.1` при работающем API.

Форма `/kontakt` теперь предназначена для отчёта: нужны только домен и email. Поля имени и произвольного сообщения убраны, чтобы не создавать видимость сохранения данных, которые этот API не обрабатывает. Для общих проектных запросов остаётся прямая почтовая ссылка. Маркетингового согласия или подписки форма не создаёт.

Для публикации нужно разместить актуальную сборку и направить `/api/` к Node backend на том же origin. Исходный `compose.yaml` и `start.sh` обслуживают прежний архивный `dist/`; они не запускают backend и не являются новым production-развёртыванием. Нужны отдельная конфигурация reverse proxy, постоянный приватный диск SQLite/outbox, рабочий исходящий DNS/HTTPS и настройка почты. Текущая реализация не заявляется готовой к публичному запуску без этих шагов.

## Границы отчёта

Модуль проверяет исходный HTML эвристиками: title, viewport, og:image, PDF-меню и ссылки Impressum/Datenschutz. Это не Lighthouse, не измерение мобильной адаптивности и не юридическое заключение. Время запроса не равно скорости загрузки страницы в браузере. HTTPS показывает транспорт полученного ответа, но не заменяет отдельный аудит TLS.

Ошибка загрузки или неподдерживаемый формат дают `score: null` и неизвестные проверки. Обнаруженная PDF-ссылка не означает, что меню существует только в PDF. Наличие юридической ссылки не подтверждает корректность документа. Загруженные HTML и комментарии не исполняются. Будущий fetcher обязан ограничивать входной размер до передачи в этот модуль.
