# KALDER: обзор архитектуры

Проверено в облачной среде 15 октября 2026 года. Архив KALDER_SITE_DEMO_v3 импортирован без изменения содержимого файлов, включая готовый `dist/`. Этот обзор добавлен отдельно.

## Устройство

Это клиентское SPA на React 18 и TypeScript. Vite 6 собирает приложение, Tailwind CSS 4 отвечает за стили, Framer Motion — за анимации. Backend, база данных, авторизация и серверный приём заявок отсутствуют.

```text
index.html → src/main.tsx → App.tsx / BrowserRouter
                            ├─ Header / Footer / ScrollToTop / SiteMeta
                            └─ pages → components
                                  ├─ config/site.ts: реквизиты и контакты
                                  └─ lib/analytics.ts: клиентские события

WebsiteCheck → URL query → Kontakt → локальное состояние формы
Vite build → статические HTML/JS/CSS → nginx / Docker Compose
```

Семь маршрутов: `/`, `/leistungen`, `/analyse`, `/projekte`, `/kontakt`, `/impressum`, `/datenschutz`. `pages/` собирает страницы из блоков `components/`. Состояние формы хранится в React; введённый адрес сайта переносится в контактную форму через query string. `SiteMeta` меняет title и description после клиентской навигации.

`trackEvent` отправляет события в существующий `window.dataLayer` и в DOM CustomEvent. Подключённого провайдера аналитики нет. Коммерческие материалы и сценарии демонстрации находятся в `docs/`.

## Оценка

Структура подходит для небольшого сайта студии: простая сборка, отдельные страницы и повторно используемые блоки, строгий TypeScript, централизованные контакты и токены оформления. Дополнительные сервисы и менеджер глобального состояния для текущего демо не нужны.

nginx настроен на SPA fallback, отдельную проверку `/healthz` и 404 для отсутствующих assets. Docker публикует порт только на loopback. Для размещения на GitHub Pages потребуется отдельно продумать base path и fallback маршрутов; загрузка в GitHub сама по себе сайт не публикует.

## Что потребуется для публичного запуска

1. Подключить реальную отправку заявок. Сейчас успешное состояние формы означает лишь локальную проверку полей. Нужен серверный обработчик или сервис форм с серверной валидацией, защитой от спама, обработкой ошибок и правилами хранения персональных данных. Ключи сервиса должны оставаться на сервере.
2. Определить продукт Website Check. Сейчас он проверяет формат URL и переводит на форму; реального сканирования нет. Если нужен автоматический сканер, он потребует отдельной серверной архитектуры, очереди и ограничений обращений к пользовательским URL.
3. Заполнить Impressum/Datenschutz и реквизиты, проверить контакты и статус демонстрационных проектов. `noindex` намеренно включён в HTML и nginx; убрать его можно после готовности к публикации.
4. Добавить автоматические проверки в CI: `npm ci`, typecheck, build и браузерный сценарий. В архиве нет тестового runner и CI. Для неизвестного маршрута отсутствует отдельная страница 404 в React Router.
5. Проверить зависимости: текущий `npm audit --omit=dev` сообщает три moderate finding — `react-router`, зависимый `react-router-dom` и `uuid`. SSR-сценарий из одного advisory здесь не используется, но обновление и проверка навигации остаются отдельной задачей. Автоматические исправления с изменением lockfile не применялись.
6. Упростить lockfile при отдельном обслуживании зависимостей: он содержит пакеты, отсутствующие среди прямых зависимостей текущего package.json, включая Recharts и UUID. Сам `npm ci` проходит. Закрепить версию Node и разделить исходники и публикуемый артефакт: сейчас `dist/` поставляется в архиве, хотя указан в `.gitignore`.
7. Учесть внешние ресурсы: фотографии загружаются с Unsplash, шрифты — с Google Fonts. Для автономного показа, приватности и предсказуемой загрузки стоит рассмотреть локальные копии с соблюдением лицензий. Для SEO можно рассмотреть prerender страниц; метаданные сейчас обновляются JavaScript.

## Фактические проверки этой сессии

- `npm ci` по исходному lockfile: успешно. Использована имеющаяся Node 24.19.0 / npm 11.9.0; README рекомендует Node 22 LTS, отдельно она не проверялась.
- `npm run typecheck` и `npm run build`: успешно. Отдельно проверена сборка в `.runtime/build`, чтобы будущие проверки не перезаписывали импортированный `dist/`.
- nginx в Docker: все семь страниц и `/healthz` возвращают 200; JS/CSS имеют корректные MIME; отсутствующий asset возвращает 404; заголовок noindex присутствует.
- Chromium: все семь страниц отрисованы без JS exceptions. Проверены ошибка URL, переход с нормализованным URL в контактную форму, ошибка незаполненной формы и успешное демосостояние.
- На главной при viewport 390×844 не обнаружено горизонтального переполнения. Это не полная визуальная или accessibility-проверка.
- Vite dev server обслуживает модули и отрисовывает контактную страницу без JS exceptions.

Для облачного Docker запуска используется игнорируемый `.runtime/cloud-compose.yaml`: он добавляет `wget -Y off` только в локальный healthcheck, поскольку унаследованный прокси направлял его запрос наружу и возвращал 403. Исходный `compose.yaml` не менялся. Локальным файлам сборки предоставлены обычные права чтения nginx. Инструкции запуска сохраняются в конфигурации облачной среды; процессы нужно запускать заново в новой задаче.
